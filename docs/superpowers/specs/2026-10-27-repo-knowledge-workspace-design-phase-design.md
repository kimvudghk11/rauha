# 3단계 설계: 저장소 지식, 여러 저장소 작업 공간, 설계 대화

- 날짜: 2026-10-27
- 상위 문서: [`docs/design/claude-team-design.md`](../../design/claude-team-design.md)
- 앞 단계: [`2026-10-25-step2-ladder-facts-chat-design.md`](2026-10-25-step2-ladder-facts-chat-design.md)
- 참고 분석: [`docs/analysis/rauha-vs-claude-code-kiro.md`](../../analysis/rauha-vs-claude-code-kiro.md) (D2 설계 팀 없음, F5 설계 산출물이 파일로 남지 않음)
- 개발 규칙: [`docs/conventions/ddd-entity-dto.md`](../../conventions/ddd-entity-dto.md)

표기: **(사용자)** 는 사용자가 직접 말한 것, **(결정)** 은 사용자가 "더 좋은 방향이 있으면 적용해서" 정하라고 맡겨 Claude가 정한 것이다. 결정은 읽으며 다르면 고친다.

## 1. 왜 만드는가

사용자는 rauha 하나를 터미널에 띄워 두고 여러 저장소를 훑고 고치는 반복 업무를 시키려 한다 **(사용자)**. 지금 rauha는 세 가지가 그 그림과 맞지 않는다.

1. **매번 저장소를 처음부터 다시 읽는다.** 기억 그래프에는 "지난 작업에서 무엇을 왜 정했나"만 남고, "이 저장소가 어떻게 생겼나"는 남지 않는다. 그래서 작업마다 접수 팀장이 파일 목록을 다시 받고 같은 파일을 다시 연다. 실행 기록 48개 기준 접수 한 번이 약 2.2만 토큰, 테스트·구현 팀원은 지금도 호출당 3.5~5.7만 토큰을 쓴다(2026-10-27 측정). 사용자는 저장소마다 diff로 최신 상태를 따라가서 다시 읽지 않기를 원한다 **(사용자)**.
2. **어느 브랜치, 어느 커밋을 보고 판단했는지 말하지 않는다.** 사용자는 읽은 것과 고친 것에 브랜치를 밝히기를 원한다 **(사용자)**.
3. **의도를 대화로 잡는 단계가 없다.** 요청이 오면 접수 팀장이 한 번 해석하고 바로 테스트·구현으로 간다. 사용자는 "설계 때는 많이 물어봐도 되고, 그 뒤로는 덜 물어보면 좋겠다. 설계가 깔끔하면 개발부터 테스트까지는 문제가 없을 것"이라고 했다 **(사용자)**. 전에 "질문이 너무 많다"고 한 것은 구현 단계의 질문이었다.
4. 여러 저장소를 한 터미널에서 다루는 방식이 없다. rauha는 띄운 폴더 하나에 묶여 있다 **(사용자: 하나의 cmd에서 여러 repo)**.

덤으로 풀리는 것: bench의 `coupon`처럼 큰 요청은 지금 "너무 큼"으로 멈춘다. 설계 단계가 큰 요청을 작은 작업으로 나누면 끝까지 갈 수 있다 **(결정)**.

## 2. 목표 / 하지 않을 것 / 실패로 보는 것

**목표**

- 저장소마다 "저장소 지식"을 한 번 만들어 두고, 다음부터는 마지막으로 본 커밋과 지금 사이의 diff만 보고 바뀐 부분만 고친다.
- 모든 답과 결과 안내서, 기억 기록에 "어느 저장소의 어느 브랜치, 어느 커밋을 보고 읽었는지, 어디를 고쳤는지"를 남긴다. 커밋하지 않은 변경을 함께 봤으면 그것도 밝힌다.
- rauha 하나로 여러 저장소를 다룬다. 질문은 여러 저장소에 걸쳐 답할 수 있고, 작업은 저장소별로 나눠 차례로 한다.
- 기능 단위 요청은 설계 대화를 먼저 한다. 설계 대화에서는 충분히 묻고, 결과를 사용자가 고칠 수 있는 설계 문서로 남겨 승인받는다. 승인 뒤의 테스트·구현·검증은 설계를 기준으로 거의 묻지 않고 진행한다.
- 큰 요청은 설계가 작은 작업(S·M급)으로 나눠서 끝까지 한다.
- 토큰: 같은 저장소를 두 번째로 다룰 때 접수 팀장의 토큰과 턴이 첫 번째보다 줄어든다(6장).

**하지 않을 것 (이번 단계)**

- 여러 작업을 동시에 실행하기. 설계가 나눈 작업은 차례로 한다(분석 F1은 다음 단계).
- rauha가 브랜치를 만들거나 커밋하기. 지금처럼 사용자가 커밋한다. 브랜치는 읽고 알릴 뿐이다 **(결정)**.
- vitest 밖의 테스트 판정(분석 F6), MCP(F3), 되돌리기(F4), IDE 연동(D3).
- 임베딩 같은 "의미로 찾기". 저장소 지식은 글과 경로로 남긴다.
- 원격 저장소(GitHub)의 다른 브랜치를 내려받아 읽기. 로컬 저장소에 있는 것만 본다.
- `-p`(한 번 실행) 모드의 설계 **대화**. `-p`는 지금처럼 바로 작업한다. 다만 `-p --design`은 묻지 않고 추천값으로 설계를 채워 바로 작업으로 나눠 실행한다(bench가 이 길을 쓴다, 6장) **(결정)**.

**실패로 보는 것 (돌아가더라도)**

- 낡은 저장소 지식을 지금 상태처럼 쓰는 것. 지식은 쓰기 직전에 반드시 지금 커밋과 맞춰 보고, 어느 커밋 기준인지 함께 넘긴다.
- 다른 저장소나 다른 브랜치의 지식이 섞이는 것.
- 승인한 설계와 다르게 만드는 것, 또는 승인 뒤에 설계로 판단할 수 있는 것을 다시 묻는 것.
- 오타 수정 같은 작은 요청까지 설계 대화를 강요하는 것.
- 설계 대화에서 한 번에 질문을 여러 개 쏟아 내는 것. 한 번에 하나씩 묻는다.
- 저장소 지식을 만드느라 처음 한 번에 쓰는 토큰이 이후 절약보다 큰 것(6장에서 잰다).
- 구독 토큰을 읽거나 옮기는 코드(CLAUDE.md 금지 사항). 화면과 답에 달러 비용을 쓰는 것(사용자 취향).

## 3. 저장소 지식

### 3.1 무엇을 남기나 (결정)

저장소마다 두 부분으로 남긴다.

1. **코드가 계산하는 사실** (모델 호출 없음): 최상위 폴더 구조와 폴더별 파일 수, 패키지 관리자와 lockfile, `package.json` 스크립트(테스트·타입 검사·린트 명령), 언어별 파일 수, 테스트 파일 위치 규칙(예: `*.spec.ts`가 소스 옆), CLAUDE.md·README 위치. 지금 `NodeChecks`가 매번 계산하는 검사 명령도 여기로 옮겨 다시 쓴다.
2. **모델이 쓰는 메모**: 영역(폴더나 모듈)별로 짧은 메모. 무엇을 하는 곳인지, 들어가는 지점(entry), 따르는 관례(오류 처리, 이름 짓기, 테스트 방식), 비슷한 일을 하는 기존 코드의 위치. 메모마다 **근거가 된 파일 경로**를 붙인다. 근거 파일이 바뀌면 그 메모만 다시 쓴다.

메모는 rauha의 근거 규칙을 따른다. 읽은 파일에 있는 것만 쓰고, 추측은 쓰지 않는다(`<no_inference>`).

지식에는 언제나 **기준**이 붙는다: 저장소 경로, 브랜치 이름, 커밋 해시, 만든 시각.

### 3.2 어디에 두나 (결정)

`~/.rauha/profiles/<프로필>/knowledge/<저장소 키>/`에 둔다. 저장소 키는 기억 파일과 같은 규칙(저장소 최상위 경로의 해시)을 쓴다. 저장소 안에 두지 않는 이유: 사용자 저장소에 커밋하지 않은 파일을 만들면 "깨끗한 작업 트리" 검사와 부딪히고, 팀 저장소를 rauha 파일로 어지럽히지 않기 위해서다.

브랜치마다 따로 두지 않고 **커밋 기준으로 하나**를 둔다. 브랜치를 바꾸면 그 브랜치의 커밋 기준으로 고친다(3.3). 지식 파일에 기록한 커밋 이후 바뀐 내용만 diff로 따라가기 때문에 브랜치를 오가도 처음부터 다시 만들 일은 드물다.

### 3.3 최신으로 맞추기

저장소 지식을 쓰기 직전(질문이나 작업이 그 저장소를 처음 건드릴 때)마다:

1. 지금 브랜치, `HEAD` 커밋, 커밋하지 않은 변경 목록을 읽는다(git, 모델 호출 없음).
2. 지식의 기준 커밋과 같고 커밋하지 않은 변경도 없으면 그대로 쓴다.
3. 다르면 바뀐 파일 목록을 구한다.
   - 기준 커밋이 지금 `HEAD`의 조상이면 `git diff --name-status <기준>..HEAD`.
   - 아니면(브랜치를 바꿨거나 rebase) 두 커밋의 merge-base 기준으로 양쪽 diff를 합친다.
   - 기준 커밋이 저장소에 없으면(지워짐) 처음부터 다시 만든다.
   - 여기에 커밋하지 않은 변경 파일을 더한다.
4. 코드가 계산하는 사실은 다시 계산한다(싸다).
5. 근거 파일이 바뀐 메모만 "낡음"으로 표시하고, haiku 팀원 한 번으로 그 파일들만 읽어 다시 쓴다. 바뀐 파일이 새 영역(메모가 없는 폴더)에 있으면 그 영역 메모를 새로 쓴다.
6. 바뀐 파일이 너무 많으면(기준: 전체 파일의 30% 이상, 또는 200개 이상) 처음부터 다시 만든다 **(결정, 숫자는 구현하며 조정 가능)**.
7. 커밋하지 않은 변경에서 만든 메모에는 "작업 트리 변경 포함"을 표시하고, 기준 커밋은 `HEAD`로 두되 다음에 다시 확인한다.

처음 만들 때는 haiku 팀원이 Read·Grep·Glob만으로 영역별 메모를 쓴다. 턴과 예산에 상한을 둔다. 대화 모드에서 저장소를 처음 쓰면 "이 저장소를 처음 파악하는 중"을 보여 준다.

### 3.4 어떻게 쓰나

- 접수 팀장과 답변 팀원, 설계 팀원(5장)에게 `<repo_knowledge repo="..." branch="..." commit="...">` 묶음을 넘긴다. 지금 접수 팀장에게 넘기는 전체 파일 목록(`<project_files>`)은 지식 안의 폴더 구조로 대신한다. 실제 코드를 확인해야 하면 지금처럼 도구로 연다.
- 묶음은 팀원 메시지의 맨 앞에 둔다. 같은 저장소를 다루는 동안 앞부분이 같아서 프롬프트 캐시가 잘 맞는다.
- 테스트·구현 팀원은 지금처럼 `<files>`와 `<checks>`를 받는다. `<checks>`는 저장소 지식의 검사 명령에서 바로 만든다.
- 작업이 끝나면 바뀐 파일로 지식을 고친다(다음 사용 때 3.3이 어차피 하지만, 방금 rauha가 고친 것은 바로 반영한다).

### 3.5 기준 밝히기 (출처)

- 답: 끝에 "읽은 기준: `<저장소> · <브랜치> (<커밋 7자>)`"를 한 줄 붙인다. 커밋하지 않은 변경을 읽었으면 "+ 작업 트리 변경". 여러 저장소를 읽었으면 저장소마다 한 줄.
- 작업 결과 안내서: "작업 기준: `<브랜치> (<시작 커밋>)`, 고친 곳: 같은 브랜치의 작업 트리(커밋 안 함)".
- 기억 그래프: 작업·질문 점에 저장소, 브랜치, 커밋을 기록한다. "아까 그 기능"으로 지난 작업을 찾을 때 후보에 브랜치를 함께 보여 준다. 지금 브랜치와 다른 브랜치의 작업이면 그렇다고 알린다.

## 4. 여러 저장소 작업 공간

### 4.1 작업 공간 정하기 (결정)

- rauha를 git 저장소 안에서 띄우면 그 저장소가 작업 공간이자 지금 저장소다. 지금과 같다.
- git 저장소가 아닌 폴더에서 띄우면, 그 아래 두 단계까지의 git 저장소를 모두 작업 공간에 넣는다(예: `~/work`에 `api`, `web`, `infra`). 지금 저장소는 비어 있다.
- `/repo`: 작업 공간의 저장소 목록과 각각의 브랜치, 지금 저장소 표시.
- `/repo <이름>`: 지금 저장소 바꾸기. `/repo add <경로>`: 작업 공간에 더하기.
- 작업 공간 구성은 띄운 폴더마다 기억해 두고 다음에 같은 폴더에서 띄우면 다시 쓴다.

### 4.2 요청이 어느 저장소 일인지

- 라우터가 메시지에서 저장소를 고른다. 작업 공간의 저장소 이름과 저장소 지식의 요약을 받아서, 메시지가 가리키는 저장소(하나 또는 여러 개)를 돌려준다.
- 메시지에 저장소가 드러나지 않으면 지금 저장소를 쓴다. 지금 저장소도 없고 하나로 정할 수 없으면 사용자에게 고르게 한다. 이건 되돌리기 어려운 쓰기 대상의 문제라서 묻는다.
- 질문은 여러 저장소에 걸쳐도 된다. 답변 팀원에게 해당 저장소들의 지식을 주고, 다른 저장소 폴더도 읽을 수 있게 한다. Agent SDK의 `additionalDirectories`(`--add-dir`과 같음, `sdk.d.ts`의 `ClaimOptions`에 있음)를 쓰는 것을 먼저 검토하고, 읽기 권한 검사(`tool-guard`)가 작업 공간 밖을 막게 한다.
- 작업은 **한 번에 저장소 하나**에서 한다. 저장소마다 지금처럼 깨끗한 작업 트리 검사, 폴더 잠금(`FileWorkLock`), 기억 파일을 따로 쓴다. 여러 저장소를 고쳐야 하는 요청은 설계 대화로 보내서 저장소별 작업으로 나눈다(5장).

### 4.3 계정(프로필)과 기억 (결정)

- **프로필은 저장소마다 정한다.** 지금 있는 폴더 규칙(`ProfileBook.resolve`)을 저장소 경로에 적용한다. 작업 공간에 회사 저장소와 개인 저장소가 섞여 있으면 각자 자기 계정(`CLAUDE_CONFIG_DIR`)으로 팀원을 부른다. 저장소 지식, 기억, 설계 문서도 그 저장소 프로필 폴더에 둔다. 회사 저장소 일이 개인 계정으로 도는 일을 막기 위해서다(상위 설계 "계정 분리").
- 팀원(`AgentSdkTeamMember`)은 프로필마다 하나씩 만들어 세션 동안 재사용한다. 미리 띄워 두기(prepare)도 프로필별로 한다.
- 한 질문이나 한 설계가 **서로 다른 프로필의 저장소에 걸치면 하지 않는다.** 이유를 알리고 프로필별로 나눠 요청하게 한다. 계정이 섞이는 것보다 한 번 더 요청하는 편이 낫다.
- **기억은 지금처럼 저장소마다 파일 하나**를 유지한다. 여러 저장소에 걸친 질문·설계는 관련 저장소의 기억 파일마다 같은 점을 남긴다(점 id가 같아 중복되지 않는다). "아까 그거"는 작업 공간의 모든 저장소 기억에서 찾고, 후보에 저장소와 브랜치를 함께 보여 준다.

### 4.4 화면

- 상태 줄에 지금 저장소와 브랜치를 보여 준다(지금은 브랜치만 있다).
- 팀원이 다른 저장소에서 일하기 시작하면 진행 줄에 저장소 이름을 붙인다.

## 5. 설계 대화

### 5.1 언제 설계 대화를 하나 (결정)

- 라우터의 판정을 `question` / `work` / `feature` 세 가지로 늘린다.
  - `feature`: 새 기능이나 동작 변경으로, 해석이 여러 갈래일 수 있거나 여러 파일·여러 저장소에 걸치는 요청.
  - `work`: 범위가 분명한 작은 수정(오타, 이름 바꾸기, 테스트 하나 추가, 명확한 버그 수정).
- 접수 팀장이 `work`로 받은 요청을 **L급**으로 판정하면(지금 "너무 큼"으로 멈추는 경우), 멈추지 않고 설계 대화로 넘긴다. **M급은 지금처럼 바로 진행한다.** 지금 잘 끝나는 M급 요청에 설계 대화를 강요하지 않기 위해서다 **(결정)**.
- 승인된 설계가 나눈 작업은 **설계가 정한 크기를 따른다.** 접수 팀장은 그 작업의 등급을 다시 매겨 멈추거나 설계로 되돌려 보내지 않는다. 설계 팀원이 작업을 S·M 크기로 나눌 책임을 진다 **(결정)**.
- 사용자가 직접 고를 수도 있다: `/design <요청>`은 설계부터, 요청에 "바로 해줘"를 붙이거나 설계 첫 질문에 "그냥 해줘"라고 하면 설계 질문을 건너뛰고 설계 팀원이 추천값으로 설계를 채워 승인만 받는다.

### 5.2 설계 팀원

- 새 역할 `designer`. 기본 sonnet, effort medium. 여러 저장소에 걸치거나 접수가 L급으로 본 요청은 opus **(결정)**. 읽기 도구만 쓴다.
- 설계 대화 동안 사용자의 입력은 라우터를 거치지 않고 설계 팀원에게 간다. `/cancel`로 설계를 그만둔다.
- 설계 팀원은 한 번에 질문 하나를 한다. 먼저 사용자가 묘사하게 하는 열린 질문을 하고, 이해한 부분은 짧게 되짚어 확인받는다. 사용자가 "알아서 해"라고 하면 추천값을 정하고 "이건 rauha가 정함"으로 표시한다. 이 흐름은 지금 이 문서를 만든 대화(brainstorming)를 본뜬다.
- 설계 팀원은 저장소 지식과 기억(지난 작업과 결정)을 받는다. 코드 확인이 필요하면 읽는다. 답에 쓰는 사실은 지금 근거 규칙을 그대로 따른다.
- 설계 대화는 여러 턴에 걸친다. 상태(지금까지의 문답, 설계 초안)는 대화 세션이 들고 있고, 팀원 호출마다 요약을 넘긴다. 같은 Agent SDK 세션을 이어 쓰는 방법(`resume`)과 매번 요약을 넘기는 방법 중 토큰이 적은 쪽을 구현 때 재서 고른다 **(결정: 구현에 맡김, 6장 기준으로)**.

### 5.3 설계 문서

- 설계가 정리되면 rauha가 설계 문서를 쓴다. 저장 위치는 저장소 지식과 같은 프로필 폴더 아래 `designs/<저장소 키>/<날짜>-<짧은 이름>.md`이고, 대화 화면에 경로를 하이퍼링크로 보여 준다 **(결정, 3.2와 같은 이유)**. 사용자가 그 파일을 직접 고친 뒤 "다시 읽어"라고 하면 고친 내용을 기준으로 한다. 저장소에 남기고 싶으면 `/design save`로 저장소의 `docs/rauha/designs/`에 복사한다(사용자가 커밋).
- 문서 내용:
  - 의도와 이유, 목표, 하지 않을 것
  - 동작 시나리오: Given/When/Then, 구체적인 값으로("10% 할인하면 10,000원이 9,000원")
  - 정한 해석: 사용자가 정한 것과 rauha가 정한 것을 구분
  - 저장소별 범위와 기준(브랜치, 커밋)
  - 작업 목록: 작업마다 저장소, 범위, 수용 기준, 순서와 앞 작업 의존. 각 작업은 S·M급 크기
  - 위험과 확인하지 못한 것
- 승인: 화면에 문서 요약과 작업 목록을 보여 주고 "승인 / 고칠 점 말하기"를 고르게 한다(선택 알림 규칙에 따라 늦게 답하면 OS 알림).

### 5.4 승인 뒤 실행

- 작업 목록을 순서대로 지금 최소 루프에 넣는다. 각 작업의 업무 지시서는 설계 문서의 해당 작업과 시나리오, 정한 해석에서 만든다. 접수 팀장은 범위와 파일을 확인하는 역할만 하고, 해석이 갈리는 지점은 설계에 비추어 정한다.
- **승인 뒤 질문 규칙**: 접수의 `needsUser`는 설계가 답하지 않는 지점이면서 되돌리기 어려운 것(돈, 데이터 삭제, 보안·권한, 공개 API, DB 구조)일 때만 묻는다. 나머지는 설계 기준으로 정하고 안내서에 남긴다. 위험 동작 허락(`tool-guard`)은 지금처럼 묻는다.
- 작업이 멈추면(`needs-support` 등) 그 작업에 의존하는 뒤 작업은 하지 않고, 의존하지 않는 작업은 계속한다. 끝에 작업별 결과를 한 화면에 모아 보여 준다.
- 작업과 작업 사이에는 사용자가 커밋할 틈이 없으므로, 앞 작업의 결과(rauha가 남긴 파일)는 지금의 `carried` 규칙으로 이어서 일한다.
- 기억 그래프에 설계 점을 만들고 작업 점들을 잇는다. "그 기능 왜 이렇게 만들었어?"에 설계 문서의 이유로 답할 수 있다.

## 6. 측정과 완료 기준

- **저장소 지식 효과**: bench에 "같은 저장소에서 두 번째 요청" 묶음을 더한다. 접수 팀장의 턴과 토큰을 지식 없이(지금)와 지식 있음으로 비교한다. 목표: 두 번째 요청의 접수 토큰이 지금보다 줄어든다. 처음 지식을 만드는 토큰도 따로 적어, 몇 번째 요청부터 이득인지 보인다.
- **최신 맞추기**: 테스트로 확인한다. 커밋 하나 뒤의 diff만 다시 읽기, 브랜치 바꾸기, rebase, 커밋하지 않은 변경, 기준 커밋이 사라진 경우.
- **출처**: 답과 안내서에 브랜치와 커밋이 항상 붙는다(테스트).
- **설계 대화**: bench의 `coupon`(지금 "너무 큼")이 설계 → 작업 나누기 → 완료까지 간다. bench는 사람이 없으므로 `-p --design`(추천값으로 설계) 길로 잰다.
- **저장소 지식 bench**: "같은 저장소에서 두 번째 요청" 묶음은 요청마다 새 연습 폴더를 만들지 않고 한 폴더에서 차례로 실행해, 저장소 지식이 이어지게 한다(기억·지식 폴더는 bench 전용 프로필 폴더를 쓴다).
- **승인 뒤 질문 수**: `coupon`을 설계 승인 뒤 실행하는 동안 사용자 질문이 0개(위험 동작 허락 제외).
- 다른 단계와 같이 `yarn typecheck`, `yarn test` 통과.

## 7. 만드는 순서 (결정)

각 단계가 혼자서도 쓸모 있게 나눈다.

0. **작은 보강** (9.2의 바로 넣을 것). 서로 독립적이고 작아서 먼저 한다.
1. **저장소 지식과 출처 밝히기** (한 저장소). 토큰 절약이 바로 나고 2·3의 바탕이다.
2. **여러 저장소 작업 공간**. 저장소 고르기, `/repo`, 여러 저장소 질문.
3. **설계 대화**. 설계 팀원, 설계 문서, 승인, 작업 나눠 실행, 여러 저장소 작업.

## 8. 구현하는 사람에게 맡기는 것

- 저장소 지식의 파일 형식(JSON과 Markdown 중), 메모 영역을 나누는 단위(폴더 깊이).
- 처음 만들기·고치기 팀원의 턴과 예산 상한 값.
- "너무 많이 바뀜" 기준 숫자(3.3의 6번).
- 설계 대화 상태를 넘기는 방법(5.2 마지막 항목), 6장 기준으로 잰 뒤 선택.
- 라우터가 `feature`와 `work`를 가르는 프롬프트 문장. bench와 실제 대화로 다듬는다.
- 화면의 세부 모양(설계 승인 화면, `/repo` 목록). 지금 대화 화면의 스타일과 Delfi를 따른다.
- 저장소에 CLAUDE.md 없이 AGENTS.md만 있을 때 팀원이 AGENTS.md를 읽는지 확인하고, 안 읽으면 읽게 한다(9.1 참고).

## 9. 다른 하네스와 비교 (2026-10-27 확인)

각 제품 공식 문서나 GitHub README를 그날 직접 열어 확인한 기능만 적는다. rauha의 현재 상태는 이 저장소 코드에서 확인했다.

### 9.1 비교표

| 기능 | 가진 곳 (확인한 출처) | rauha 지금 | 처리 |
| --- | --- | --- | --- |
| 설계 → 작업 나누기 → 실행 | Kiro specs(requirements·design·tasks), superpowers(brainstorming·writing-plans) | 없음 | 이 문서 5장 |
| 저장소 요약을 매번 넣기 | Kiro steering(product·tech·structure, 항상 포함), Aider repo map(파일별 핵심 심볼, 기본 1k 토큰), Plandex(tree-sitter 프로젝트 지도) | 없음 | 이 문서 3장 + 9.2 |
| 세션을 넘는 자동 기억 | Claude Code auto memory(저장소별, 세션마다 앞 200줄·25KB 읽음) | 작업 결정만 기억(사용자 교정·취향은 안 배움) | 다음 단계 |
| 되돌리기(체크포인트) | Claude Code `/rewind`, Kiro checkpoints, Cline checkpoints | 없음(사용자가 git으로) | 다음 단계 |
| 비밀 파일 막기 | Kiro `.kiroignore` | 없음(`tool-risk.ts`에 규칙 없음) | 9.2 |
| 내 변경 검토 명령 | Codex CLI(커밋 안 한 변경·커밋·브랜치를 리뷰, 작업 트리는 안 고침) | 리뷰어는 rauha 작업 안에서만 | 9.2 |
| 세션 이어 가기 | Codex `codex resume`, Claude Code `/resume` | 없음(`/update`하면 대화가 끊김) | 9.2 |
| 독립 작업 병렬 실행 | Kiro(의존 그래프로 "wave" 단위 동시 실행), Claude Code·Codex·opencode 서브에이전트 | 차례로만 | 다음 단계(분석 F1) |
| MCP | Claude Code, Kiro, Codex, Cline | 없음 | 다음 단계(분석 F3) |
| 실행 격리(샌드박스) | Codex(read-only·workspace-write 등), OpenHands(대화마다 Docker) | 위험 명령 허락 묻기만 | 다음 단계 |
| 이미지 입력 | Codex `--image` | 없음 | 다음 단계 |
| 변경을 따로 두고 승인 뒤 반영 | Plandex(누적 diff 검토 샌드박스) | 작업 트리에 바로 쓰고 사용자가 커밋 | 하지 않음(지금 방식 유지) |
| 여러 모델 공급자 | opencode, Cline, OpenHands | Claude만 | 하지 않음(구독 안에서 쓰는 게 목표) |

rauha가 이미 앞선 것(다른 곳에서 같은 형태를 확인하지 못한 것): 테스트를 코드가 잠그고 코드가 판정하는 TDD, 팀원 주장의 근거를 코드가 확인하는 사실 점검, haiku부터 시작해 실패하면 올리는 승격 사다리, 폴더 규칙으로 계정을 나누는 프로필.

### 9.2 이번에 같이 넣는 것 (결정)

- **코드가 만드는 심볼 지도** (Aider·Plandex 방식): 저장소 지식(3.1)의 "코드가 계산하는 사실"에 파일별로 내보내는 이름(함수·클래스·타입)을 더한다. 모델 메모보다 싸고 diff로 바로 고칠 수 있다. 처음에는 TypeScript·JavaScript만 하고, 파싱 방법(TypeScript 컴파일러 API 등)은 구현에 맡긴다.
- **비밀 파일 막기**: `.env`, `*.pem`, `*.key`, `id_rsa*` 같은 기본 목록과 저장소의 `.rauhaignore`에 맞는 파일은 팀원이 읽지도 쓰지도 못하게 `tool-guard`에서 거절한다. 저장소 지식에도 넣지 않는다.
- **`/review`**: 커밋하지 않은 내 변경(또는 브랜치)을 리뷰어에게 보여 주고 근거가 확인된 지적만 보고한다. 파일은 고치지 않는다. 지금 리뷰어와 사실 점검을 그대로 쓴다.
- **세션 이어 가기**: 대화 세션의 앞 대화 요약과 이어 일할 파일을 저장해 두고, `rauha --continue`(또는 `/update` 뒤 자동)로 이어 간다.
